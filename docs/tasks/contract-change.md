# Задача для агента: изменение и расторжение контракта (ст. 95 44-ФЗ)

Бриф модуля «Внесение изменений и расторжение контракта». Читать вместе с
`AGENTS.md` соседнего репозитория `csms`: фронт показывает форму и карточку,
бэкенд хранит документ, его редакции и журнал.

## Зачем

В реестре контрактов была только карточка контракта. Изменение существенных
условий и расторжение — отдельная процедура со своими основаниями, сроками и
комплектом документов. Если её не хранить, нельзя ответить на вопросы
контролёров: на каком основании менялась цена, что согласовали, кто подписал,
когда документ зарегистрирован в ЕИС.

Модуль закрывает эту дыру: черновик → согласование → подпись → регистрация в
ЕИС, с проверками по каждому шагу и неизменяемым журналом.

## Границы модуля

- **Снимок контракта приходит с фронта** из реестра контрактов. Модуль не
  читает json-server и не подменяет цену или статус контракта «своими»:
  документ должен читаться и после того, как карточку контракта изменят.
- **Домен не знает про HTTP и БД**: правила и переходы — в
  `Csms.Domain`, сценарии — в `Csms.Application`, хранение — в
  `Csms.Infrastructure`, маршруты — в `Csms.Api`.
- **Статус нельзя «поставить» через API**: отдельного `PUT /status` нет.
  Статус меняет только сценарий домена, иначе проверки ст. 95 обходились бы
  одним запросом.

## Модель

`ContractChange` — небольшая машина состояний:

```
Черновик → На согласовании → Согласован → Подписан → Зарегистрирован в ЕИС
     ↑            ↓
     └────── Отклонён (новая редакция)     Отменён — из любого незарегистрированного
```

- `ContractChangeDocument` — соглашение, уведомление, решение, судебный акт,
  приложение. Хранит текст, номер редакции и **SHA-256 содержимого**: по нему
  видно, что подписанная версия совпадает с согласованной.
- `ContractChangeEvent` — журнал аудита: кто, когда, из какого статуса в какой,
  что именно сделал. Только дописывается.
- `ContractChangeInput` — снимок контракта и предлагаемые условия. Обязательность
  полей проверяют правила, а не DTO: ошибка одинакова и в форме, и при
  сохранении.

## Основания (каталог — часть правил)

Код — устойчивый ключ для API и хранения; от него зависят обязательные поля.

| Код | Норма | Что допускает |
| --- | --- | --- |
| `price_reduction` | ч. 1 ст. 95 | Снижение цены без изменения объёма |
| `quantity_10` | ч. 1 ст. 95 | Объём ±10 %, цена — не выше +10 % |
| `quality_improvement` | ч. 1 ст. 95 | Улучшение характеристик без роста цены |
| `government_act` | ч. 1 ст. 95 | Сроки и условия по акту органа власти |
| `price_formula` | ч. 1 ст. 95 | Цена по формуле |
| `unit_price` | ч. 24 ст. 22, ст. 95 | Цена единицы при неопределённом объёме |
| `supplier_replacement` | ч. 17.1 ст. 95 | Замена поставщика на неисполненную часть |
| `bank_support` | ч. 1 ст. 95 | Сопровождение контракта |
| `by_agreement` | ч. 8 ст. 95 | Расторжение по соглашению сторон |
| `court_decision` | ч. 8 ст. 95 | Расторжение по решению суда |
| `customer_unilateral` | ч. 9–13 ст. 95 | Односторонний отказ заказчика |
| `supplier_unilateral` | ч. 20–22 ст. 95 | Односторонний отказ поставщика |
| `force_majeure` | ст. 451 ГК, ч. 8 ст. 95 | Существенное изменение обстоятельств |

Проверки не верят присланным с фронта флагам: они берут их из каталога по коду.

## Правила, которые нельзя обойти

- Менять и расторгать можно только `signed`, `in_execution`, `suspended`:
  завершённый или расторгнутый контракт повторно не трогаем.
- Дата документа не раньше даты контракта; дата расторжения — не раньше даты
  документа.
- Основание должно соответствовать виду: изменение и расторжение не смешиваются.
- Причина — не короче 10 символов.
- `quantity_10`: объём — не более ±10 %, цена — не выше +10 %.
- `price_reduction` и `quality_improvement`: цена только снижается.
- `government_act`: нужны номер и дата акта; только по нему меняется срок
  исполнения.
- `unit_price`: цена единицы не выше начальной максимальной цены.
- Односторонний отказ: номер и дата уведомления, расторжение — не ранее чем
  через **10 дней** с даты уведомления (ч. 13 ст. 95).
- Комплектность проверяется по целевому статусу: на согласовании уже нужен
  документ требуемого вида (для одностороннего отказа решение заказчика
  равнозначно уведомлению).
- Регистрация в ЕИС требует реестрового номера контракта.
- Расхождение хеша содержимого с сохранённым — блокирующая ошибка: текст
  правили после согласования.

## API

`/api/contract-changes` (тег «Изменение и расторжение контрактов»):

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/` | Список, фильтры `organizationId`, `contractId`; свежие сверху |
| GET | `/bases` | Каталог оснований с флагами |
| GET | `/meta` | Статусы, виды, типы документов, срок 10 дней |
| POST | `/validate` | Проверить условия без сохранения (те же правила) |
| GET | `/{id}` | Карточка с документами, журналом и текущими замечаниями |
| POST | `/` | Создать черновик |
| PUT | `/{id}` | Изменить черновик или отклонённый документ |
| POST | `/{id}/documents` | Добавить документ |
| DELETE | `/{id}/documents/{documentId}` | Удалить документ из черновика |
| POST | `/{id}/submit` | Отправить на согласование |
| POST | `/{id}/approve` | Согласовать |
| POST | `/{id}/reject` | Отклонить с причиной |
| POST | `/{id}/sign` | Подписать |
| POST | `/{id}/register` | Зафиксировать регистрацию в ЕИС |
| POST | `/{id}/cancel` | Отменить незарегистрированный документ |

`Issues` в ответе отдаются всегда, а не только при ошибке: интерфейс показывает
предупреждения до отправки, а не после отказа сервера.

## Хранение

- Схема `contract`: `contract_changes`, `contract_change_documents`,
  `contract_change_events` (каскадное удаление дочерних строк).
- `EIS_STORE=postgres` — `EfCoreContractChangeRepository`, иначе
  `InMemoryContractChangeRepository` (сценарии и правила те же, записи не
  переживают перезапуск).
- **Оптимистичная блокировка — колонка `Revision`**, увеличивается хранилищем
  при каждой успешной записи. `xmin` остаётся дополнительной защитой на уровне
  PostgreSQL.
- Миграции: `AddContractChanges` (таблицы) и `AddContractChangeRevision`
  (ревизия; существующие строки получают 1).

## Найденные при проверке дефекты (исправлены)

1. **`Submit` и `RegisterInEis` проверяли правила предыдущего статуса.**
   В черновике комплектность документов не требуется, поэтому документ без
   соглашения уходил на согласование и «застревал» там. Теперь проверка идёт по
   целевому статусу.
2. **Оптимистичная блокировка не работала.** `SaveAsync` перечитывал строку и
   брал свежий `xmin`, поэтому `WHERE ... AND xmin = ...` всегда совпадал:
   вторая правка молча перезаписывала первую. Введена ревизия записи, которая
   известна документу с момента чтения. Та же схема с `xmin` осталась в
   хранилище пакетов ЕИС — там её стоит проверить отдельно.

## Проверка

```
set "EIS_TEST_DB=Host=localhost;Port=5433;Database=csms_eis;Username=postgres"
dotnet test tests/Csms.Tests --nologo -v q
```

Без `EIS_TEST_DB` интеграционные тесты на PostgreSQL пропускаются, остальные
идут на памяти. Покрыто: каталог оснований, правила изменения и расторжения,
машина состояний и журнал, сценарии сервиса (включая конфликт правки),
контракты HTTP-слоя, EF-хранилище (перезапуск, фильтры, конфликт).

## Что осталось

- Фронт: форма по `/bases` и `/meta`, карточка с журналом, предпросмотр
  замечаний через `/validate`.
- Выгрузка соглашения и уведомления в XML ЕИС — по образцу пакетов ЕИС, когда
  появится схема нужного документа.
- Проверить блокировку в хранилище пакетов ЕИС: там остался прежний `xmin`-подход.
