# Задача для агента: электронное актирование (приёмка по ст. 94 44-ФЗ)

Бриф модуля «Электронное актирование». Читать вместе с `AGENTS.md`: фронт
формирует документ о приёмке и подписывает его, бэкенд хранит документ, его
позиции, недостатки и журнал.

## Зачем

До этого модуля приёмка в системе не была реализована: в `WorkPlan.md`
(п. 3.4.3) она помечена как отложенная, а карточка контракта хранила только
настройки приёмки (порядок, срок, экспертиза, комиссия). Самого документа о
приёмке не было — значит нельзя ответить на вопросы контролёров: что принято,
в каком количестве, по какой цене, была ли экспертиза, кто подписал итог и
когда документ зарегистрирован в ЕИС.

Модуль закрывает этот разрыв: поставщик формирует документ, заказчик проводит
экспертизу и подписывает итог приёмки, документ регистрируется в ЕИС.

## Границы модуля

- **Снимок контракта и условий приёмки приходит с фронта** из реестра
  контрактов: модуль не читает json-server и не подменяет цену или статус
  контракта «своими». Приёмку нельзя пересчитать задним числом по изменённой
  карточке.
- **Домен не знает про HTTP и БД**: правила и переходы — в `Csms.Domain`,
  сценарии — в `Csms.Application`, хранение — в `Csms.Infrastructure`,
  маршруты — в `Csms.Api`.
- **Статус нельзя «поставить» через API**: отдельного `PUT /status` нет.
  Статус меняет только сценарий домена, иначе проверки ст. 94 обходились бы
  одним запросом.
- **Обмен с ЕИС не имитируется.** Пока не сделан маппинг на
  `IntegrationEATypes.xsd` (`elActUnstructuredSupplierTitleType`,
  `elActUnstructuredCustomerTitleType`, `acceptanceResultCodeType`) и SOAP
  `getEADocs`, модуль хранит документ и его итог, но не выдаёт «правильный на
  вид» XML.

## Модель

`ContractAcceptance` — машина состояний:

```
Черновик → Направлен заказчику → Принято (код ЕИС 1)
                              → Принято с расхождениями (код ЕИС 2)
                              → Мотивированный отказ (код ЕИС 3)
                              → Возвращено для уточнения (код ЕИС 0)
                                        ↓
                              Черновик (новая редакция) → снова на согласование
Принято / Принято с расхождениями → Зарегистрирован в ЕИС
Отменён — из любого незарегистрированного статуса
```

- `AcceptanceResult` хранит **коды ЕИС** (`acceptanceResultCode`): 0 —
  возвращено для уточнения, 1 — принято без расхождений, 2 — принято с
  расхождениями, 3 — не принято. Пересчитывать смысл статуса на границе API не
  нужно.
- `AcceptancePosition` — позиция принятого: наименование, ОКПД2, единица,
  количество, цена за единицу **с НДС**, ставка НДС (0, 5, 7, 10, 20 %), страна
  происхождения, реестровая запись. НДС и стоимость без налога считаются из
  цены с НДС, а не вводятся отдельно — иначе сумма позиции и сумма документа
  расходятся.
- `AcceptanceDefect` — выявленный недостаток: описание, количество, требование
  (заменить, устранить, уменьшить цену, не принимать). Ссылка на позицию
  необязательна: недостаток может касаться документа в целом.
- `AcceptanceEvent` — журнал аудита: кто, когда, из какого статуса в какой.
  Только дописывается.

## Правила ст. 94 44-ФЗ

- Приёмка возможна только по `signed`, `in_execution`, `suspended`:
  исполненный или расторгнутый контракт повторно не принимают.
- Дата документа не раньше даты контракта.
- **Срок приёмки — от 1 до 20 рабочих дней** (ч. 13 ст. 94). Предельный срок
  рассмотрения документа заказчиком считается от даты документа и отдаётся в
  API (`reviewDeadline`).
- **Экспертиза** (ч. 3 ст. 94): своими силами или с привлечением экспертов.
  Если контракт её не предусматривал, стороннюю организацию привлекать нельзя.
  Для сторонней экспертизы нужны организация, номер и дата заключения, причём
  заключение не может быть позже даты документа.
- **Приёмочная комиссия** (ч. 6 ст. 94): если предусмотрена, нужны номер и дата
  решения о её создании.
- **Мотивированный отказ** должен быть мотивирован: причина не короче
  10 символов и перечень недостатков.
- Приёмка **без расхождений** не может содержать претензии; приёмка
  **с расхождениями** без недостатков невозможна.
- Недостаток не может быть заявлен на количество больше принятого — ни по одной
  позиции, ни суммарно по позиции.
- Сумма документа не может превышать цену контракта (для корректировочного
  документа — не блокируется, его проверяет заказчик).
- Корректировочный документ требует реквизитов исправляемого документа и
  причины исправления; дата не раньше исправляемого.
- Регистрация в ЕИС требует реестрового номера контракта.

Правила вызываются при сохранении, направлении заказчику, подписании итога и
регистрации — по **целевому** статусу, а не по текущему: иначе документ без
позиций уходил бы в работу.

## API

`/api/acceptances` (тег «Электронное актирование»):

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/` | Список, фильтры `organizationId`, `contractId`, `status`; свежие сверху |
| GET | `/meta` | Статусы, виды, коды итога, требования по недостаткам, ставки НДС, срок 20 дней |
| POST | `/validate` | Проверить условия без сохранения (те же правила) |
| GET | `/{id}` | Карточка с позициями, недостатками, журналом и текущими замечаниями |
| POST | `/` | Создать черновик |
| PUT | `/{id}` | Изменить черновик или возвращённый документ |
| POST | `/{id}/positions` | Добавить позицию |
| DELETE | `/{id}/positions/{positionId}` | Удалить позицию из черновика |
| POST | `/{id}/defects` | Зафиксировать недостаток |
| DELETE | `/{id}/defects/{defectId}` | Снять недостаток |
| POST | `/{id}/submit` | Направить документ заказчику |
| POST | `/{id}/accept` | Подписать итог приёмки (`result`: 1 или 2) |
| POST | `/{id}/refuse` | Оформить мотивированный отказ |
| POST | `/{id}/return` | Вернуть документ на уточнение |
| POST | `/{id}/register` | Зафиксировать регистрацию в ЕИС |
| POST | `/{id}/cancel` | Отменить незарегистрированный документ |

`Issues` в ответе отдаются всегда, а не только при ошибке: интерфейс показывает
предупреждения до отправки, а не после отказа сервера. В ответе также итоги
(`totalWithVat`, `vatAmount`, `totalWithoutVat`) и `reviewDeadline`.

## Хранение

- Схема `contract`: `contract_acceptances`, `acceptance_positions`,
  `acceptance_defects`, `acceptance_events` (каскадное удаление дочерних строк).
- `EIS_STORE=postgres` — `EfCoreAcceptanceRepository`, иначе
  `InMemoryAcceptanceRepository` (сценарии и правила те же, записи не
  переживают перезапуск).
- **Оптимистичная блокировка — колонка `Revision`**, увеличивается хранилищем
  при каждой успешной записи. `xmin` остаётся дополнительной защитой на уровне
  PostgreSQL.
- Позиции и недостатки неизменяемы: правка идёт через удаление и добавление,
  порядок задаёт `OrderIndex`. Журнал только дописывается.
- Миграция: `AddContractAcceptance`.

## Фронтенд

- `src/services/Acceptance/acceptance.types.ts` + `acceptance.api.ts` — типы
  ответов csms-api и хуки: список/карточка, `meta`, `validate`, создание и
  правка, позиции, недостатки, действия `submit/refuse/return/cancel`,
  подписание итога и регистрация в ЕИС.
- `src/components/ContractAcceptance/` — реестр с фильтрами по статусу и
  контракту, форма реквизитов и условий, карточка с позициями, недостатками,
  итогами, действиями, историей и печатью акта.
- Роуты: `/acceptances`, `/acceptances/new`, `/acceptances/:id`,
  `/acceptances/:id/edit`. В карточке реестра контрактов — кнопка «Приёмка»
  с предзаполнением `?contractId=…`.
- Интеграция со ст. 95: в карточке приёмки — ссылки на изменения/расторжения
  по контракту, в карточке изменения — ссылки на приёмки. Оба реестра читают
  `contractId` из query, поэтому переход сохраняет фильтр.

## Проверка

```
set "EIS_TEST_DB=Host=localhost;Port=5433;Database=csms_eis;Username=postgres"
dotnet test tests/Csms.Tests --nologo -v q
```

Без `EIS_TEST_DB` интеграционные тесты на PostgreSQL пропускаются, остальные
идут на памяти. Покрыто: правила приёмки и сроки в рабочих днях, машина
состояний и журнал, сценарии сервиса (включая конфликт правки), контракты
HTTP-слоя, EF-хранилище (перезапуск, фильтры, синхронизация позиций и
недостатков, конфликт).

## Что осталось

- Маппинг документа на `IntegrationEATypes.xsd` и отправка/получение через
  SOAP `getEADocs` — по образцу пакетов ЕИС, когда появится рабочая схема
  обмена. До этого `isPlaceholderFormat` для XML приёмки не выставляется:
  XML просто не формируется.
- Подписание документа КЭП на фронте: домен хранит подписанта и время, но
  проверку открепленной подписи делает фронт (как и для контракта).
- Состав приёмочной комиссии: сейчас фиксируются только решение о её создании;
  персональный состав — следующий шаг (связь с графиком отпусков).
- Связка с оплатой (ч. 13.1 ст. 34): срок оплаты считается от даты подписания
  документа о приёмке, отдельного модуля оплаты пока нет.
- Корректировочные документы с отрицательными суммами (сторно) — сейчас
  корректировка перераспределяет позиции, но не принимает отрицательных
  количеств.
