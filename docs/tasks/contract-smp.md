# Привлечение субъектов малого предпринимательства в реестре контрактов

Этот бриф описывает серверную часть карточки «Сведения о привлечении СМП/СОНКО»
контракта: правила, статусы, API и хранение. Клиентская логика живёт в `csms`
(`src/services/ContractSmp`), а формат обмена — в `contractSmp.schema.ts`.

## 1. Что именно автоматизировано

Сведения о договорах субподрядчика, которые закрывают обязательство по ч. 5–6
ст. 30 44-ФЗ и типовым условиям ПП РФ от 23.12.2016 № 1466:

- реквизиты договора или документа (номер, дата, сумма, ОКПД2, вид цены,
  предмет, период);
- данные субподрядчика (наименование, ИНН, КПП, признак СМП/СОНКО);
- даты получения сведений от подрядчика, подписания акта и оплаты;
- декларация о принадлежности к СМП/СОНКО и копии документов-оснований;
- подтверждения достоверности подрядчиком и заказчиком;
- принятие/отклонение заказчиком и фиксация выгрузки в ЕИС;
- расчёт фактического объёма привлечения и неустойки за недобор.

Снимок контракта (организация, номер, наименование, цена, процент привлечения)
сохраняется вместе с записью: карточка в реестре может измениться, а сведения
должны читаться в том виде, в каком их подавали.

## 2. Нормативная база

| Источник | Что используется |
|---|---|
| ч. 5–6 ст. 30 44-ФЗ | обязательный объём привлечения СМП/СОНКО |
| ПП РФ от 23.12.2016 № 1466, п. 2–6 | сроки предоставления документов, подтверждения и неустойка 0,1 % за каждый день недобора |
| ч. 3 ст. 103 44-ФЗ | 3 рабочих дня на размещение полученных сведений в ЕИС |
| карта XSD 17.0 | реквизиты блока `subContractorsnfo` / `zfcs_contract2015SubContractInfoType`: сумма, наименование, ИНН, КПП, статус `SMP\|SONO` |

Схемы 658 и 918 в поставке ЕИС отсутствуют, поэтому генерация целевого XML
по СМП не реализована: модуль хранит реквизиты карточки и факт выгрузки. Это
не «заглушка формата», а описание объективного ограничения; см.
`docs/eis-open-questions.md`.

## 3. Домен

- `ContractSmpEnums.cs` — `ContractSmpDocumentType`, `ContractSmpStatus`,
  `ContractSmpPriceType`, русские подписи. Значения перечислений сериализуются
  в camelCase: `subContract`, `pushedToEis`, `contract`, `unit`.
- `ContractSmpRules.cs` — единый набор проверок: реквизиты контракта, даты,
  суммы, ИНН/КПП/ОКПД2, подтверждения, обязательные поля для статуса
  `Accepted`/`PushedToEis`, хеши документов. Ошибки (`error`) блокируют
  сохранение, предупреждения (`warning`) показываются в карточке.
- `ContractSmpRecord.cs` — машина состояний. Статус меняется только методами
  `Accept`, `Reject`, `Resubmit`, `PushToEis`; правка (`Update`) доступна в
  `Submitted`/`Rejected`. Каждый переход заново прогоняет правила и пишет
  событие. `Revision` — токен оптимистичной блокировки.
- `ContractSmpDocument.cs` — документ-основание с SHA-256: по хешу видно,
  что выгруженная в ЕИС редакция не переписана.
- `ContractSmpVolume.cs` — расчёт объёма и неустойки, каталог сроков. В объём
  идут только **принятые** записи типа `subContract` с `isSmpSubject = true`.

### Статусы

| Статус | Смысл | Разрешённые действия |
|---|---|---|
| `submitted` | сведения поданы подрядчиком | правка, документы, удаление, принять, отклонить |
| `accepted` | заказчик проверил и принял | выгрузка в ЕИС; правка и удаление запрещены |
| `pushedToEis` | выгрузка зафиксирована | только чтение |
| `rejected` | заказчик вернул на доработку | правка, документы, удаление, повторная подача |

Статуса `draft` нет: frontend-схема его не содержит, создание уже означает
подачу сведений.

## 4. API

Группа `/api/contract-smp-records` (аналогично `/api/contract-changes`):

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/` | список, фильтры `organizationId`, `contractId`; свежие сверху |
| GET | `/meta` | статусы, типы документов/цен, сроки № 1466 и 44-ФЗ |
| GET | `/volume` | объём привлечения, недобор, неустойка (`contractId`, `contractPrice`, `requiredPercent`, `overdueDays`) |
| POST | `/validate` | проверить форму без сохранения |
| GET | `/{id}` | карточка с документами, журналом и замечаниями |
| POST | `/` | подать сведения → `submitted` |
| PUT / PATCH | `/{id}` | изменить поданные/отклонённые сведения |
| DELETE | `/{id}` | удалить неподтверждённую запись |
| POST / DELETE | `/{id}/documents[/{documentId}]` | документы-основания |
| POST | `/{id}/accept`, `/reject`, `/resubmit`, `/push-to-eis` | действия; прямого `PUT /status` нет |

Ответ — плоский DTO в полях frontend-схемы: даты строками `yyyy-MM-dd` /
`yyyy-MM-ddTHH:mm:ss`, деньги строками (`"1200000"`), перечисления camelCase.
Дополнительные поля (`status`, `revision`, `documents`, `events`, `issues`)
клиентской схемой игнорируются, но доступны для отладки и журнала.

PUT и PATCH принимают **полный снимок** записи (как и в модуле изменений
контракта): домен заменяет `Input` целиком и заново проверяет правила. Клиент,
переходя с `json-server`, обязан слать все поля из `ContractSmpRecordSchema`,
а не только изменённые поля — иначе обязательные реквизиты исчезнут.
Действия меняют статус только через `/accept`, `/reject`, `/resubmit`,
`/push-to-eis`, поэтому прямого `PUT /status` нет.

Слои: `Csms.Domain` (правила и машина состояний) → `Csms.Application`
(`ContractSmpRecordService`, команды, интерфейс репозитория) → `Csms.Infrastructure`
(EF/in-memory репозитории) → `Csms.Api` (DTO и маршруты). Сервис и репозитории
регистрируются в `Program.cs` вместе с `EIS_STORE=memory|postgres`.

## 5. Хранение

Миграция `AddContractSmpRecords` создаёт в схеме `contract`:

- `contract_smp_records` — снимок контракта, реквизиты, статус, метки времени,
  `revision` и системный `xmin` для оптимистичной блокировки;
- `contract_smp_record_documents` — документы с хешем и порядком;
- `contract_smp_record_events` — журнал изменений (только дописывается).

Индексы: `(organizationId, contractId)`, `contractId`, `status`,
`documentType`, `supplierInn`. Удаление записи каскадно удаляет документы и
журнал. EF-репозиторий при сохранении сверяет ожидаемую ревизию; конфликт
преобразуется в `ContractSmpStoreConflictException`, а сервис — в понятную
ошибку «обновите страницу».

In-memory репозиторий используется в режиме `EIS_STORE=memory` и в тестах;
набор правил и сценариев идентичен PostgreSQL.

## 6. Тесты

- `ContractSmpRulesTests` — проверки обязательных полей, подтверждений, реквизитов
  ЕИС, объёма, неустойки и каталога сроков.
- `ContractSmpWorkflowTests` — переходы статусов, документы, хеши, запрет
  правки после принятия.
- `ContractSmpServiceTests` — сценарии приложения, фильтры, удаление и расчёт
  объёма на in-memory хранилище.
- `ContractSmpContractsTests` — разбор строк запроса и совместимость JSON ответа
  с frontend-схемой.
- `ContractSmpPostgresTests` — интеграция с локальным PostgreSQL (`EIS_TEST_DB`):
  сохранение/чтение после «перезапуска» и отклонение устаревшей ревизии.

Команды:

```bash
dotnet build
dotnet test
$env:EIS_TEST_DB='Host=localhost;Port=5433;Database=csms_eis;Username=postgres'; dotnet test
```

## 7. Ограничения и не сделано намеренно

- Реальная генерация XML для карточки ЕИС невозможна без схем 658/918 —
  сохраняются реквизиты и факт выгрузки, маппер остаётся `placeholder-v0`.
- Сервер не читает json-server фронта: снимок контракта приходит в запросе,
  как и в модуле изменений контракта.
- Даты оплаты, акта и получения сведений проверяются на согласованность, но
  календарь рабочих дней и расчёт конкретных сроков показывает `/meta`;
  автоматический расчёт дедлайнов по выходным не подменяет решение инспектора.
